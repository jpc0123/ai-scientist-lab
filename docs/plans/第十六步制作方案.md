# 第十六步制作方案：v1.6 受限源码补丁建议与沙箱验证

> **本文档为 v1.6 权威实现方案。**  
> 承接 `第十五步制作方案.md`（v1.5 LLM 质量治理）。  
> Tag 基线：`v1.5.0` @ `79f350a`；分支：`feat/v1.6-restricted-source-patching`。  
> **原则：** LLM 只生成补丁建议；默认不改主工作区；禁止直接 commit/push/任意 shell；人工审批不变；规则校验优先于 LLM。  
> **封版后：** v1.5 只接受修复；新功能进入本分支。

---

## 0. 目标与问题边界

### 0.1 v1.5 已解决

模型输出质量、安全、成本、延迟可评测；未通过 Quality Gate 的 Profile 不能用于正式规划。

### 0.2 v1.6 要解决

在**质量与安全体系已就绪**的前提下，允许 LLM 提出**受限源码补丁建议**，经白名单、静态检查、人工审批与沙箱验证后，才可能进入实验证据链。

### 0.3 LLM 禁止事项（硬约束）

LLM **不能**：

- 直接修改主工作区  
- 直接 `git commit` / `git push`  
- 执行任意 shell  
- 修改 Docker、密钥、CI 或安全配置  
- 绕过人工审批  

### 0.4 最终交付定义

> Scientist Lab 能够从 Evidence Gap / Failure 出发，由 Mock（及后续受限真实 Provider）生成 `PatchProposal`（Unified Diff），经路径白名单、静态安全检查与人工审批后，仅在临时工作区应用并跑单测/沙箱实验，产出 `PatchEvidence`；是否合并仍由人工决定。

### 0.5 不做（本版本延期）

- LLM 自动合并到主分支  
- 任意仓库级重构  
- 无审批的热修复  
- 多仓库联邦补丁  
- Web 控制台补丁工作流（可后置）

## 1. 核心主链

```text
Evidence Gap / Failure
→ LLM 生成 PatchProposal
→ 路径与文件白名单检查
→ Unified Diff 解析
→ 静态安全检查
→ 人工审批
→ 临时工作区应用补丁
→ 单测与沙箱实验
→ 生成 PatchEvidence
→ 人工决定是否合并
```

## 5. 数据模型（摘要）

```python
class PatchProposal(BaseModel):
    patch_id: str
    project_id: str
    status: Literal[
        "draft", "proposed", "verified", "rejected_by_verifier",
        "approved", "rejected", "applied_sandbox", "failed_sandbox",
        "evidence_recorded", "merged", "discarded"
    ]
    title: str
    rationale: str
    evidence_gap_ids: list[str]
    unified_diff: str
    files_touched: list[str]
    fingerprint_sha256: str
    provider: str  # mock | ...
    verification_json: dict
    approval_json: dict | None
    created_at: str
    updated_at: str
```

**本阶段（v1.6.1–1.6.3）不实现真正应用补丁。**  
`approved` 仅表示人工同意进入后续沙箱阶段，不写主工作区。
